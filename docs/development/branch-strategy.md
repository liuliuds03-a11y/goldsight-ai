# GoldSight AI V3.0 - 分支策略

## 概述

本项目采用 **main + develop + feature/\*** 的分支模型，确保开发流程清晰、版本可追溯、发布稳定可靠。

## 分支类型

### 1. `main` — 主分支（生产就绪）

- **用途**：始终反映最新的生产环境稳定版本
- **保护规则**：
  - 禁止直接推送，仅通过 Pull Request 合并
  - 合并前必须通过 PM Agent 验收
  - 每次合并自动打 Tag（语义化版本号）
- **来源**：仅从 `develop` 或 `release/*` 分支合并

### 2. `develop` — 开发集成分支

- **用途**：日常开发的集成分支，包含下一个版本的所有功能
- **保护规则**：
  - 禁止直接推送，仅通过 Pull Request 合并
  - 合并前需通过 CI 检查（lint、测试）
- **来源**：从 `feature/*` 分支合并

### 3. `feature/*` — 功能开发分支

- **命名规范**：`feature/<模块>-<简述>`
  - 示例：`feature/backend-user-auth`、`feature/frontend-dashboard`
- **用途**：各 Agent 在独立分支上开发特定功能
- **生命周期**：
  1. 从 `develop` 创建
  2. 开发完成后提交 PR 到 `develop`
  3. 合并后删除功能分支
- **提交频率**：每个有意义的完成单元提交一次

### 4. `hotfix/*` — 紧急修复分支（按需）

- **命名规范**：`hotfix/<问题简述>`
- **用途**：修复生产环境紧急问题
- **生命周期**：
  1. 从 `main` 创建
  2. 修复完成后同时合并到 `main` 和 `develop`
  3. 合并后删除

## Agent 分支职责

| Agent | 主要操作分支 | 说明 |
|-------|-------------|------|
| 版本管理 Agent | `main`、`develop` | 分支管理、版本发布、Tag 标记 |
| 后端 Agent | `feature/backend-*` | 后端功能开发 |
| 前端 Agent | `feature/frontend-*` | 前端功能开发 |
| 数据库 Agent | `feature/database-*` | 数据库迁移与优化 |
| 部署 Agent | `main`（只读） | 基于 main 分支部署 |

## 规则总结

1. **不直接在 `main` 或 `develop` 上开发**
2. **每个功能一个分支**，完成后合并、删除
3. **合并必须通过 PR**，附带审查和 CI 检查
4. **提交信息遵循项目提交规范**（见 `commit-convention.md`）
5. **发布版本使用语义化标签**（v1.0.0、v1.1.0 等）
